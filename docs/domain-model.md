# Аудит доменных контрактов перед ЭТАПОМ 4

Проверено по `backend/app/models.py`, `backend/app/profile_schemas.py`, `backend/app/profile_api.py`, `frontend/lib/onboarding-store.ts` и `frontend/app/onboarding/page.tsx`. Это описание текущего состояния; модели, API и алгоритмы в рамках аудита не менялись.

| Контракт | Статус | Что хранится сейчас |
| --- | --- | --- |
| `UserProfile` | Достаточно по составу полей | `housing_goal` (`buy`/`rent`/`compare`), `purchase_budget`, `rent_budget`, `initial_payment`, `comfortable_monthly_payment`, тип семьи, число взрослых и детей, возраст детей в JSONB, автомобиль, способы передвижения, горизонт и будущие изменения. Публичный ID — UUID; внутренний PK остаётся целочисленным. |
| `PartnerProfile` | Неполный | Отдельно хранятся имя, рабочая координата, транспорт, словарь предпочтений и жизненные цели. Явной связи с несколькими собственными `LifePoint` нет. |
| `LifePoint` | Поля достаточны, владелец неоднозначен | Тип (`kind`), имя (`label`), координаты PostGIS `location`, частота `visits_per_week`, важность. API переводит их в `type`, `name`, `latitude`/`longitude`, `frequency_per_week`, `importance`. Каждая точка связана только с `user_profile_id`. |
| `AnalysisRequest` | Неполный для воспроизводимого расчёта | Есть связь с профилем, статус, время создания и отдельные nullable `user_score`, `partner_score`, `family_score`. Нет зафиксированного снимка входных данных и версий расчёта/данных. |
| Frontend → backend | Совпадает по структуре основного payload | `payloadFromDraft()` передаёт поля `ProfileCreate`, вычисляет `children_count`, убирает UI-поле `localId`, преобразует пустые бюджеты и текст в `null`, передаёт `partner_work` как `partner.work_point`. Значения валидируются Pydantic. |

## Пробелы, важные для scoring engine

1. **Принадлежность точек партнёру теряется.** `partner_work` остаётся в общем списке точек профиля и дополнительно сохраняется как `PartnerProfile.work_location`. Но другая точка партнёра (`parents`, `university`, `other`) не имеет владельца. По `kind` можно угадать только специальный случай работы партнёра. Для отдельных маршрутов и score каждого взрослого нужен явный контракт владельца точки.
2. **Запрос анализа ссылается на изменяемые данные.** После создания `AnalysisRequest` endpoint `POST /api/life-points` может изменить координаты, частоту и важность. Запрос хранит только ссылку на профиль, поэтому повторный расчёт может получить другие входы. До запуска scoring engine нужно определить неизменяемый снимок входного профиля и точек, версию алгоритма и версии использованных данных либо иной механизм воспроизводимости.
3. **Предпочтения партнёра неоднозначны.** UI показывает значение `50` для неустановленных слайдеров партнёра, но в `partner.preferences` записывает только изменённые ключи. Pydantic принимает произвольный словарь. Нужно зафиксировать на backend допустимые ключи и значение по умолчанию, чтобы scoring engine не зависел от поведения интерфейса.
4. **Финансовые ограничения могут отсутствовать.** Для покупки Pydantic требует `purchase_budget`, но `initial_payment` и `comfortable_monthly_payment` остаются необязательными. До ипотечного или платёжного расчёта нужно определить, допустимы ли отсутствие и нулевой взнос и как они интерпретируются. Для аренды обязателен `rent_budget`.

UI-поля `step` и `localId` не являются аналитическими входами. Остальные основные ответы анкеты сохраняются в backend. Однако из-за пунктов 1–3 пока нельзя гарантировать, что scoring engine сможет восстановить все нужные значения только из устойчивого backend-контракта без дополнительных предположений.

**Вывод:** текущие контракты достаточны для анкеты и хранения запроса, но не готовы к ЭТАПУ 4. Сначала нужно согласовать принадлежность точек, семантику предпочтений партнёра и воспроизводимый состав `AnalysisRequest`. Этот аудит не реализует scoring engine.
