# Аналитические контракты перед ЭТАПОМ 4

## Профиль и точки жизни

`UserProfile` хранит сценарий покупки или аренды, бюджеты, первоначальный взнос, состав семьи и возраст детей, транспорт, горизонт планирования и будущие изменения. `PartnerProfile` хранит собственные транспорт, предпочтения, цели и рабочую координату. Публичный ID профиля — UUID, внутренние связи используют целочисленные ключи.

`LifePoint` хранит тип, название, координаты PostGIS, частоту посещения и важность. `user_profile_id` объединяет точки одного профиля. Владелец каждой точки задаётся отдельно:

| `owner_type` | `primary_user_id` | `partner_profile_id` |
| --- | --- | --- |
| `primary_user` | ID основного профиля | `NULL` |
| `partner` | `NULL` | ID профиля партнёра |

Ограничение БД требует ровно одного владельца, соответствующего `owner_type`. API проверяет, что партнёр принадлежит тому же общему профилю. Frontend передаёт `owner_type` для каждой точки, включая точки партнёра, независимо от типа места.

## Предпочтения и уверенность

Каноническое значение каждого предпочтения — `PreferenceValue`:

```json
{"value": null, "is_answered": false, "source": "default", "confidence": 0}
```

После явного ответа пользователя, например:

```json
{"value": 90, "is_answered": true, "source": "user", "confidence": 1}
```

Для ответа партнёра используется `source: "partner"`. Диапазон `value` — 0–100, `confidence` — 0–1. Валидация запрещает числовое значение и положительную уверенность без ответа; ответ требует значение, источник человека и положительную уверенность. UI показывает «Не указано», пока человек не выбрал значение. Нажатие «Указать значение» создаёт явный ответ 50; сброс возвращает `null`.

`UserPreferences.preference_values` (JSONB) и `PartnerProfile.preferences` (JSONB) содержат эту структуру для всех 17 ключей, включая три компромисса (`price_vs_time`, `today_vs_future`, `car_dependency`). Унаследованные числовые колонки `UserPreferences` и `UserProfile` nullable и не имеют default 50; `weights` хранит только явно отвеченные значения. Старые числовые данные без признака ответа не позволяют определить намерение пользователя, поэтому миграции помечают их как неотвеченные в каноническом JSONB.

## Неизменяемый запрос анализа

`POST /api/analysis/request` вызывает `create_analysis_snapshot()` и сохраняет в `AnalysisRequest` JSONB поля `profile_snapshot`, `partner_snapshot`, `life_points_snapshot`, `preferences_snapshot`, `data_version_snapshot`. Первые четыре копируют текущее состояние анкеты и точек; последнее содержит версии, даты, контрольные суммы и размеры всех зарегистрированных источников данных. Запрос не читает эти значения повторно из изменяемого профиля. Изменение координат через `/api/life-points` не меняет уже созданный снимок.

Запросы, созданные до этой миграции, получают пустые снимки: их прежнее состояние восстановить нельзя. `status` и поля score остаются заготовкой; расчёт и scoring engine в рамках этого изменения не создаются.

## Frontend → backend

`payloadFromDraft()` передаёт контракт `ProfileCreate`: `children_count` вычисляется из списка детей, UI поле `localId` удаляется, каждая точка содержит `owner_type`, предпочтения передаются как `PreferenceValue`. Сервер хранит все необходимые входы для будущего расчёта. `step` и локальный ID точки остаются только в браузере.
